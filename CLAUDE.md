### Epic 4 conventions established

- **Multi-screen wizards** (clarify now, review wizards later in Epic 9) extend `templates/components/focus_card_base.html`, not `base.html` directly — it supplies the progress bar, step counter, dimmed backdrop, and window-level `1`–`9` digit-key + Esc handling (Esc navigates to Inbox; digit keys click `[data-wizard-key]` elements). A screen fills `wizard_label`/`wizard_heading`/`wizard_helper`/`wizard_body`.
- **Wizard progress** is not DB-backed: `request.session["clarify_processed"]` counts decisions made this session; total is recomputed each render as `processed + still-unprocessed count`, so items captured mid-session extend the total instead of corrupting it.
- **Inline tag parsing** lives in `core/tagging.py` (`extract_tags`, `sync_tags_from_text`) — reusable anywhere free text should yield `@context`/`#tag` M2M relations (Epic 5 will reuse it). The regex deviates from the plan's literal spec by requiring `@`/`#` at start-of-text or after whitespace, so email addresses and URL fragments aren't misread as tags.
- **Tag typeahead** (`static/js/tag-typeahead.js` + `core/partials/field_tagged.html`) is a separate, client-side-only suggestion layer over existing `Tag` names — use `field_tagged.html` instead of `field.html` for any free-text field that accepts `@`/`#` tokens; requires the view to pass `all_tags` (a JSON string of `[{name, is_context}]`, see `core/clarify.py::_all_tags_json`) and the field's widget to carry `TAG_FIELD_ATTRS` from `core/forms.py`.
- **Multi-step forms with client-validation-that-can-fail** (e.g. clarify's Project screen requiring ≥1 subtask): re-render the same screen with the bound form/errors on failure rather than redirecting, so the user's in-progress input (including Alpine-managed repeater rows) isn't lost. See `core/clarify.py::_clarify_form_screen` and `_project_extra_context`.
- Whenever `static/css/input.css` or any template introduces Tailwind classes not yet in the compiled output, rebuild with `.bin/tailwindcss.exe -i static/css/input.css -o static/css/app.css --minify` before relying on it (Tailwind only emits classes it scans in use).

### Epic 5 conventions established

- **View modules are split per concern, not one big `views.py`**: `core/lists.py` (Today/Week/Month/Tasks/Waiting/Someday/Trash + generic row actions like complete/move/reorder), `core/projects.py` (project list/detail/subtasks), `core/tags.py` (tag manager). Follow this pattern for new screens rather than growing `views.py` — pick the module by *domain*, not by HTTP verb.
- **Badge vocabulary (`docs/design.md` §6) is a Python dict, not template conditionals**: `core/templatetags/gtd_extras.py`'s `{% badge kind=... n=... %}` inclusion tag is the only place badge class strings are assembled, so `tailwind.config.js`'s `content` list had to explicitly add `./core/templatetags/**/*.py` — otherwise Tailwind's scanner never sees those literal class tokens (they're not in any `.html` file) and silently drops them from the compiled CSS. Any future Python-assembled class strings need the same treatment.
- **Django's `default` template filter is not a safe "unless explicitly False" guard** — it substitutes on *any* falsy value (`False`, `0`, `""`, `None`), so `{{ x|default:True }}` silently turns an explicit `False` back into `True`. Use `default_if_none` when the caller needs to pass a real boolean (see `components/task_row.html`'s `show_complete`). Bit us once already (Trash rows briefly showed a complete-circle they shouldn't have) — caught by `WaitingSomedayTrashTests.test_trash_row_hides_complete_circle`.
- **Row-level HTMX actions that leave the current list** (move to Someday/Waiting/Trash, Waiting's Got it, Someday's Activate, Trash's Restore) render a persistent (non-auto-fading) confirmation line with an Undo button, rather than the 150ms-fade-then-vanish pattern used for plain completion — Undo needs the row to stay clickable, and 150ms isn't enough time for a human. See `core/templates/core/partials/task_row_moved.html` and `_MOVE_TARGET_KEYWORDS` in `core/lists.py` for how Undo finds its way back to the correct origin list.
- **`<body hx-boost="true">` means `DOMContentLoaded` fires once, ever.** Any vendored JS that needs to (re-)initialize on every navigation (e.g. SortableJS in `static/js/sortable-lists.js`) must listen for `htmx:load` instead, which fires once for the initial page and again for every boosted/swapped-in fragment.
- **`core/management/commands/`** now exists for cron-style logic (`rollover.py` first). Commands take an `--as-of YYYY-MM-DD` override where synthetic-date testing matters — don't gate cron logic on `timezone.now()` directly if a test will need to simulate "it's the 1st of the month."
- **Known scope cuts** (documented rather than silently dropped): task_row.html's ⋮ menu omits "Edit" (no plain task-edit screen exists yet in any epic — "Convert to note" was added in Epic 6); `/tasks`' single flat SortableJS container doesn't perfectly disambiguate drops between different projects' subtask groups (falls back to "front of my own group" — see task-breakdown.md Epic 5 for detail).

### Epic 6 conventions established

- **New third-party dependency:** `Markdown` (PyPI) added to `requirements/base.txt` for rendering `Note.body` — first non-Django/psycopg/environ dependency. Rendered via `core/templatetags/gtd_extras.py::markdownify` (extensions `extra` + `nl2br`), styled with a hand-rolled `.prose-note` CSS class in `static/css/input.css` (no `@tailwindcss/typography` plugin, per the no-build-pipeline rule) — rebuild `app.css` after touching those rules same as any other Tailwind change. No HTML-sanitization pass on rendered markdown: reasonable only because this is single-author, single-viewer content (the same person authors and reads every note) — do not carry this assumption into any future multi-user or externally-sourced content path.
- **`Note.search` (the Postgres `SearchVectorField`) is kept current by a `post_save` signal**, not by overriding `Note.save()` — see `core/signals.py`, registered via `CoreConfig.ready()` in `core/apps.py`. The handler uses `Note.objects.filter(pk=...).update(...)` rather than `instance.save()` specifically to avoid re-triggering `post_save` (infinite recursion) and to skip bumping `updated_at` again. Follow this same pattern (signal + `.update()`) for any other derived/denormalized field that needs to stay in sync with model saves.
- **File-upload tests must override `MEDIA_ROOT`** to an isolated temp directory (`@override_settings(MEDIA_ROOT=...)`, see `NoteScreenSmokeTests` in `core/tests.py`) — Django's test transactions roll back the database between tests, but `FileSystemStorage` writes are not transactional, so uploaded test files otherwise accumulate for real in the project's `media/` directory. Caught this after a first test run actually left a file behind on disk.
- **Tag-bearing M2M copies use direct `.set()`/`.add()` of `Tag` objects, not a text re-parse through `sync_tags_from_text`**, when the source already has the tags as an M2M relation rather than as inline `@`/`#` text (e.g. `core/notes.py::task_convert_to_note` copying a Task's tags onto its new Note). Reserve `sync_tags_from_text` for genuinely free-text fields.

### Epic 8 conventions established

- **New third-party dependencies:** `google-auth`, `google-auth-oauthlib`, `google-api-python-client`, `cryptography` — all in `requirements/base.txt`. Every GCal-touching function is gated on `core.google_calendar.get_credential()` (or `GoogleCredential.objects.exists()`) returning something — with nothing connected, the app is fully local-only and every such function is a no-op. Check `settings.GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`FERNET_KEY` before assuming OAuth is actually configured (`core.google_calendar.google_configured()`).
- **`GoogleCalendarClient` (`core/google_calendar.py`) is the only place that talks to the real Google API** — a thin wrapper whose methods (`insert_event`/`patch_event`/`delete_event`/`list_events`/`watch`/`create_gtd_calendar`) build one `googleapiclient` service call each. Everything else (timeblocks.py, recurring.py) calls through this wrapper rather than touching `googleapiclient`/`google.oauth2` directly, so tests can mock at one consistent boundary.
- **Mock-patch target must be where the name is *used*, not where it's *defined*, for plain functions/variables imported via `from x import y`** — `from core.google_calendar import sync_calendar` in a management command creates an independent name binding in that command's own module namespace, so `@patch("core.google_calendar.sync_calendar")` does NOT affect what the command actually calls; it has to be `@patch("core.management.commands.sync_gcal.sync_calendar")`. This does *not* apply to patching a **class method** (e.g. `GoogleCalendarClient.insert_event`) — a class is a single shared mutable object, so patching it via any dotted path that reaches the same class object works regardless of which module's import statement got you there. Got bitten by this omitting the fix on the first test run; if a mock silently "doesn't take" (real code path executes, e.g. a real network call error surfaces), check this first.
- **A DateField/TimeField/IntegerField assigned a raw string from `request.POST` holds that raw string until the model is next loaded from the DB** — Django's field type coercion (`str` → `datetime.time`/`int`/etc.) happens in `to_python`/`from_db_value` on the way *out* of the database, not on plain Python attribute assignment. If a view saves a model and then immediately does further logic against that *same in-memory instance* expecting typed values (as `core/recurring.py::_save_template` does, calling `_sync_gcal_event(template)` right after `template.save()`), parse `request.POST` values to their real types *before* assigning them, or `refresh_from_db()` first. Caught two real `TypeError`s this way (`block_start_time`, `block_duration_min`) that unit tests surfaced before they could ever hit a real Google account.
- **FullCalendar 6 is the one deliberate exception to the "no CDN" rule** (confirmed in this file's planning-session notes) — loaded only on `core/templates/core/calendar.html` via `{% block extra_head %}`, not globally in `base.html`. Its container listens for `htmx:load` (not `DOMContentLoaded`) for the same `hx-boost` reason as `static/js/sortable-lists.js` in Epic 5.

The full `/calendar` page does get real FullCalendar with drag/resize.

## Product summary

A single-user, self-hosted Getting Things Done (GTD) task system for Sudipto: capture → clarify → organize → reflect → engage, with two-way Google Calendar time-blocking, guided review wizards with an Eisenhower triage board, ntfy push notifications, and a stats page.

**Planned stack** (per `solution-plan.md`): Django 5.x + HTMX + Alpine.js + Tailwind CSS (standalone CLI, no bundler, output committed) + PostgreSQL. Single app `core`. No Celery/queue — background work runs via cron-triggered `manage.py` commands (see the cron table in Step 12). Deployed like the existing `tracker.sudipto.dev` pattern: EC2 Ubuntu, gunicorn + nginx + systemd.

## Architecture (once implemented)

Five subsystems inside one Django project/app-server:
1. **Core GTD engine** — models (`Task`, `InboxItem`, `Note`, `Tag`, `Area`), clarify wizard, contexts/tags, horizons (`today`/`this_week`/`this_month`/`anytime`), manual sort ordering.
2. **Recurrence engine** — `RecurringTemplate` → materialized `Task` instances (one per occurrence), overdue instances pile up rather than replacing each other.
3. **Calendar subsystem** — Google OAuth, dedicated secondary "GTD" calendar (write target) + primary calendar read-only busy overlay, two-way sync via webhook + 15-min polling fallback, missed-block detection.
4. **Reflect subsystem** — `ReviewConfig`/`ReviewSession`, guided weekly/monthly wizards, lighter quarterly/yearly checklists, the Eisenhower board (drag-only, in-review, never persisted as task metadata), Big-3 stars, carry-over decision gate.
5. **Notification subsystem** — ntfy.sh dispatch with per-kind dedupe (`NotificationLog`) and digest batching.

Key domain rules to preserve when implementing (see `solution-plan.md` Step 2 "Semantics to enforce in code"):
- A project is `Task(is_project=True, parent=None)`; subtasks are one level deep only (enforced by a `CheckConstraint`).
- Next-action resolution is a single queryset helper: explicit flagged subtask(s) → else first incomplete subtask by `sort_order` (marked `implicit=True`) → else project state `NEEDS_ATTENTION`.
- There is no stored priority/quadrant field anywhere — priority is manual `sort_order` + weekly `big3` stars (auto-cleared each review) + a transient `q2_week` chip (expires the following Monday). The Eisenhower board is a review-time-only UI, not a data model.
- Trash is a soft-delete (`list=TRASH` / `trashed_at`), purged by cron after 30 days.

## Design system rules (from `docs/design.md`)

- No dynamically-constructed Tailwind class names (`bg-{{ color }}` is forbidden because of purge) — status→class mappings must return full literal strings, added to the Tailwind safelist.
- Badges are a closed vocabulary (§6 of `design.md`) — don't invent new badge/color pairings without updating that file first.
- Dark mode is out of scope for v1; don't add `dark:` variants.
- All dates/times render in Asia/Dhaka, mono typeface.
- HTMX handles all mutations (server returns partials); Alpine is for local UI state only, never a data source — the server is truth.
