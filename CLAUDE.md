### Epic 4 conventions established

- **Multi-screen wizards** (clarify now, review wizards later in Epic 9) extend `templates/components/focus_card_base.html`, not `base.html` directly — it supplies the progress bar, step counter, dimmed backdrop, and window-level `1`–`9` digit-key + Esc handling (Esc navigates to Inbox; digit keys click `[data-wizard-key]` elements). - **Wizard progress** is not DB-backed: `request.session["clarify_processed"]` counts decisions made this session; total is recomputed each render as `processed + still-unprocessed count`, so items captured mid-session extend the total instead of corrupting it.

- **Multi-step forms with client-validation-that-can-fail** (e.g. clarify's Project screen requiring ≥1 subtask): re-render the same screen with the bound form/errors on failure rather than redirecting, so the user's in-progress input (including Alpine-managed repeater rows) isn't lost. - Whenever `static/css/input.css` or any template introduces Tailwind classes not yet in the compiled output, rebuild with `.bin/tailwindcss.exe -i static/css/input.css -o static/css/app.css --minify` before relying on it (Tailwind only emits classes it scans in use).

### Epic 5 conventions established

- **View modules are split per concern, not one big `views.py`**: `core/lists.py` (Today/Week/Month/Tasks/Waiting/Someday/Trash + generic row actions like complete/move/reorder), `core/projects.py` (project list/detail/subtasks), `core/tags.py` (tag manager). Follow this pattern for new screens rather than growing `views.py` — pick the module by *domain*, not by HTTP verb.
- **Badge vocabulary (`docs/design.md` §6) is a Python dict, not template conditionals**: `core/templatetags/gtd_extras.py`'s `{% badge kind=... n=... %}` inclusion tag is the only place badge class strings are assembled, so `tailwind.config.js`'s `content` list had to explicitly add `./core/templatetags/**/*.py` — otherwise Tailwind's scanner never sees those literal class tokens (they're not in any `.html` file) and silently drops them from the compiled CSS. Any future Python-assembled class strings need the same treatment.
- **Django's `default` template filter is not a safe "unless explicitly False" guard** — it substitutes on *any* falsy value (`False`, `0`, `""`, `None`), so `{{ x|default:True }}` silently turns an explicit `False` back into `True`. Use `default_if_none` when the caller needs to pass a real boolean (see `components/task_row.html`'s `show_complete`). Bit us once already (Trash rows briefly showed a complete-circle they shouldn't have) — caught by `WaitingSomedayTrashTests.test_trash_row_hides_complete_circle`.
- **Row-level HTMX actions that leave the current list** (move to Someday/Waiting/Trash, Waiting's Got it, Someday's Activate, Trash's Restore) render a persistent (non-auto-fading) confirmation line with an Undo button, rather than the 150ms-fade-then-vanish pattern used for plain completion — Undo needs the row to stay clickable, and 150ms isn't enough time for a human. See `core/templates/core/partials/task_row_moved.html` and `_MOVE_TARGET_KEYWORDS` in `core/lists.py` for how Undo finds its way back to the correct origin list.
- **`<body hx-boost="true">` means `DOMContentLoaded` fires once, ever.** Any vendored JS that needs to (re-)initialize on every navigation (e.g. SortableJS in `static/js/sortable-lists.js`) must listen for `htmx:load` instead, which fires once for the initial page and again for every boosted/swapped-in fragment.
- **`core/management/commands/`** now exists for cron-style logic (`rollover.py` first). Commands take an `--as-of YYYY-MM-DD` override where synthetic-date testing matters — don't gate cron logic on `timezone.now()` directly if a test will need to simulate "it's the 1st of the month."
- **Known scope cuts** (documented rather than silently dropped): task_row.html's ⋮ menu omits "Edit" (no plain task-edit screen exists yet in any epic — "Convert to note" was added in Epic 6); `/tasks`' single flat SortableJS container doesn't perfectly disambiguate drops between different projects' subtask groups (falls back to "front of my own group" — see task-breakdown.md Epic 5 for detail).

### Epic 8 conventions established

- **New third-party dependencies:** `google-auth`, `google-auth-oauthlib`, `google-api-python-client`, `cryptography` — all in `requirements/base.txt`. Every GCal-touching function is gated on `core.google_calendar.get_credential()` (or `GoogleCredential.objects.exists()`) returning something — with nothing connected, the app is fully local-only and every such function is a no-op. Check `settings.GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`FERNET_KEY` before assuming OAuth is actually configured (`core.google_calendar.google_configured()`).
- **`GoogleCalendarClient` (`core/google_calendar.py`) is the only place that talks to the real Google API** — a thin wrapper whose methods (`insert_event`/`patch_event`/`delete_event`/`list_events`/`watch`/`create_gtd_calendar`) build one `googleapiclient` service call each. Everything else (timeblocks.py, recurring.py) calls through this wrapper rather than touching `googleapiclient`/`google.oauth2` directly, so tests can mock at one consistent boundary.
- **Mock-patch target must be where the name is *used*, not where it's *defined*, for plain functions/variables imported via `from x import y`** — `from core.google_calendar import sync_calendar` in a management command creates an independent name binding in that command's own module namespace, so `@patch("core.google_calendar.sync_calendar")` does NOT affect what the command actually calls; it has to be `@patch("core.management.commands.sync_gcal.sync_calendar")`. This does *not* apply to patching a **class method** (e.g. `GoogleCalendarClient.insert_event`) — a class is a single shared mutable object, so patching it via any dotted path that reaches the same class object works regardless of which module's import statement got you there. Got bitten by this omitting the fix on the first test run; if a mock silently "doesn't take" (real code path executes, e.g. a real network call error surfaces), check this first.
- **A DateField/TimeField/IntegerField assigned a raw string from `request.POST` holds that raw string until the model is next loaded from the DB** — Django's field type coercion (`str` → `datetime.time`/`int`/etc.) happens in `to_python`/`from_db_value` on the way *out* of the database, not on plain Python attribute assignment. If a view saves a model and then immediately does further logic against that *same in-memory instance* expecting typed values (as `core/recurring.py::_save_template` does, calling `_sync_gcal_event(template)` right after `template.save()`), parse `request.POST` values to their real types *before* assigning them, or `refresh_from_db()` first. Caught two real `TypeError`s this way (`block_start_time`, `block_duration_min`) that unit tests surfaced before they could ever hit a real Google account.
- **FullCalendar 6 is the one deliberate exception to the "no CDN" rule** (confirmed in this file's planning-session notes) — loaded per-template via `{% block extra_head %}` (`core/templates/core/calendar.html`, `core/templates/core/project_detail.html`, `core/templates/core/task_detail.html`), never globally in `base.html`. The Calendar time panel markup itself lives in one shared partial, `components/calendar_time_panel.html` — both detail pages `{% include %}` it (`with task=project` from project_detail.html, since its own context variable is named `project`; task_detail.html's is already named `task`, no remapping needed) rather than duplicating it, since blocking calendar time was never actually project-specific at the model/view layer, only the UI hadn't caught up.
- **The mini-calendar's init JS is `static/js/calendar-time-panel.js`, loaded once globally from `base.html` — deliberately NOT an inline `<script>` inside the partial.** First draft put it inline; that re-executes every time the partial is boosted-swapped in, permanently stacking a new `document`-level `htmx:load` listener on every visit (listeners registered on `document`/`document.body` persist across boosted navigations - only the swapped content changes, per the same `hx-boost` reasoning `static/js/sortable-lists.js` documents from Epic 5). Because listeners of the same type fire in registration order, the *oldest* stacked listener - with that visit's `events` JSON frozen in its own closure from however long ago - could still win a "skip if already initialized" `dataset` guard and block a newer, correctly-updated listener from ever running. Symptom: a newly created block always saved correctly (the server-rendered text list next to the calendar proved that), but never appeared on the calendar grid itself after the first page load in a session. Fix: one persistent listener (registered exactly once, like `sortable-lists.js`), reading events fresh every firing from a `data-events="{{ blocks_json }}"` attribute (not `|safe` - same reasoning as `field_tagged.html`'s `tagTypeahead` JSON, §Epic 4 above) rather than a per-visit script closure, so there is no stale snapshot to ever win a race. `calendar_time_panel.html`'s own comment cross-references this.
- **Scope cut later reversed:** the project detail "Calendar time" panel's "Add block" originally shipped as a plain start/end form only, with a second embedded mini-FullCalendar widget deliberately cut as "not worth the complexity given this environment has no browser access to visually verify it anyway." That environment gained real browser automation (Playwright) later, and manual two-field datetime entry turned out to be genuinely painful in practice — so the mini calendar was added after all: `project_detail.html` now embeds a `selectable: true` FullCalendar (existing blocks shown read-only for context, `select` fills the still-present manual form's hidden fields and calls `form.requestSubmit()` — not `.submit()`, which bypasses the DOM `submit` event `hx-boost` needs). The manual form stays, collapsed behind a `<details>` "Enter exact times instead," for slot precision finer than FullCalendar's default drag-snap. Same `timeblock_create`/`timeblock_delete` endpoints as before, unchanged.

### Epic 9 conventions established

- **`ReviewSession.phase_state` (a `JSONField`) is the resumability mechanism, not the Django session** — unlike the clarify wizard (Epic 4), which tracks progress in `request.session` because it's a single uninterrupted sitting, a review can legitimately span logins/devices, so its "which phase am I on" state has to live in the DB. `core/reviews.py`'s `_get_or_create_session`/`_advance` pair is the whole mechanism: fetch-or-create the one in-progress `ReviewSession` for a cadence, and advancing writes `phase_state["phase"]` forward through a fixed ordered list (`WEEKLY_PHASES`, `MONTHLY_PHASES`, etc.). Visiting a phase URL that isn't the current one redirects to wherever the session actually is.
- **A "hard gate" phase must reject the advance server-side, not just hide the Next button** — `_weekly_carryover`'s `"next" in request.POST and not task` check means a direct POST bypassing the UI still can't skip past unresolved carried-over items. If a future phase needs the same "cannot proceed" property, gate it the same way: compute whether the blocking condition still holds *at POST time*, not just at render time.
- **A drag-and-drop action that needs more than one piece of information from the user is two HTTP round-trips, not one** — the Eisenhower board's Q2 (needs a time slot) and Q3/Q4 (need which of 2 mutations) drops POST with no extra params on the initial drop and get back a small inline form/choice partial instead of an immediate mutation; a *second* POST (from that partial, now carrying `slot_start` or `action`) does the actual mutation. Don't let the first POST guess or default an action just because a value's absent — render the choice UI instead. (Q1 is the one exception: it's a pure read+display, no user input needed, so it's a single round-trip.)
- **Global page furniture wired via a context processor gets checked against real logic, not left as a hardcoded stub** — `inbox_count`/`review_age_days` in the header trust strip had been placeholder defaults (`|default:"0"`, `"—"`) since Epic 1's scaffold with a comment saying a later epic would wire them; nobody had actually done it by Epic 9, when the "Last review: N days ago" banner needed real data anyway. `core/context_processors.py::trust_strip` (registered in `TEMPLATES` `OPTIONS.context_processors`) is the fix — add new global-chrome data there, not by threading extra context through every view.
- **When a spec attributes specific copy to an external source document, verify that document actually exists in the repo before treating the copy as fixed/authoritative** — `solution-plan.md` cites `gtd-detailed-study.md` for the "GTD tip" strip's pitfall one-liners; that file isn't in this repo. Wrote generic placeholder copy instead of fabricating text as if quoted from a source that can't be checked — flagged clearly in `docs/task-breakdown.md` and here rather than silently presenting invented copy as sourced.

- **One management command per notification kind**, matching the established one-command-per-cron-job convention (Epics 5/7/8) rather than a single mega-notifier: `notify_review_reminders`, `notify_review_overdue`, `notify_follow_up_digest`, `notify_recurring_overdue`; `missed_block` reuses Epic 8's existing `detect_missed_blocks` command since that's already the right cadence and already has the wiring point (`_notify_missed_block`) left for exactly this.

### Epic 11 conventions established

- **A metric with no natural event log gets reconstructed from existing timestamps, not a new denormalized table** — `core/stats.py::_inbox_zero_event_count` has no "inbox reached zero" event anywhere to query, so it replays every `InboxItem`'s `created_at`(+1)/`processed_at`(-1) as a sorted event stream and counts transitions to zero. This is still "live aggregate queries, no denormalized tables" per this step's own spec — just computed in Python over existing rows instead of pure SQL. Reach for this pattern before adding a new table just to make a stat easy to compute.
- **`Task.objects.create(created_at=..., ...)` (or any `auto_now_add`/`auto_now` field) silently ignores the kwarg** — Django forces those fields to "now" inside `save()` regardless of what's passed to `.create()`. To backdate a fixture row for a test, create it first, then `Model.objects.filter(pk=...).update(created_at=...)` — `.update()` is a raw SQL UPDATE that bypasses the field's save()-time override. First draft of `test_inbox_zero_event_count` passed `created_at=` straight into three `.create()` calls, which would have silently tested the wrong timeline — caught by re-reading the test's own fixture setup, not by a failure (all three rows just landed at "now", which happened to still produce a passing-but-meaningless result).
- **Chart.js joins FullCalendar as a second confirmed CDN exception** to the no-CDN rule, loaded only on `core/templates/core/stats.html` via `{% block extra_head %}` — same reasoning as Epic 8 (a full charting/calendar library isn't worth self-hosting for one page in a personal project). Keep using the `htmx:load` listener pattern (not `DOMContentLoaded`) for any page-specific JS init, per the `hx-boost` gotcha documented in Epic 5.

### Epic 12 conventions established

- **`deploy/` holds ops config as version-controlled templates** (`gtd.service`, `nginx-gtd.conf`, `crontab.txt`, `DEPLOY.md`) — reviewed/generated here, but never *applied* to a real server by the agent. Keep these in sync with reality as new cron commands or URL routes get added in future work; `crontab.txt` in particular had drifted stale by the time this epic reconciled it (it predated several commands from Epics 8/10).
- **A production dependency that a dev checkout doesn't need (here, `boto3`) gets imported lazily inside the function that uses it, not at module top** — `core/management/commands/backup_database.py` only imports `boto3` inside `_upload`/`_prune_old_backups`, so `manage.py` (and the whole test suite) still loads fine on a dev machine that only ran `pip install -r requirements/base.txt`. Same reasoning applies to any future prod-only dependency.
- **`django.test.utils.setup_test_environment()` forces `settings.DEBUG = False` for every test, unconditionally** — regardless of the project's real `.env`. A test that specifically wants to exercise `DEBUG=True` behavior (here, `core/notes.py::note_attachment_download`'s dev-mode direct-file-serving branch) needs an explicit `@override_settings(DEBUG=True)`; don't assume "the dev settings" apply just because `.env` has `DEBUG=True`. First draft of `test_dev_mode_streams_file_directly` didn't have this override and silently got the prod-mode branch instead, which is a `HttpResponse` and doesn't have `.streaming_content` like `FileResponse` does — the `AttributeError` is what surfaced it, not a logic assertion.
- **A private-file-serving view checks auth itself and never trusts nginx's `alias` path to be unreachable by luck** — `note_attachment_download` is the *only* path to a `NoteAttachment`'s bytes; `nginx-gtd.conf` deliberately has no `location /media/` block at all (only the `internal`-only `/protected-media/` one that only an `X-Accel-Redirect` response header can route to), so a stray/forgotten public alias can't reintroduce a leak later.

### Desktop capture client (`desktop/`, post-v1)

- **`desktop/` is a separate Tauri 2 app, not part of the Django project** — the only coupling to the server is an HTTP POST to `/api/capture` with a `CaptureToken` bearer token. It has no Django imports, no DB access, and no model knowledge beyond "title + description → InboxItem". Keep it that way: it's a capture surface, and anything that would make it a place you *browse* belongs in the web app.
- **All fallible logic (HTTP, disk, queue) lives in `src-tauri/src/main.rs`; the webview is a dumb form.** `ui/app.js` calls `invoke("capture", …)` and renders whatever Rust reports — it never constructs a request or decides a retry. Add new behavior on the Rust side and expose it as a `#[tauri::command]` rather than reaching for `fetch` in the frontend (which the CSP blocks anyway).
- **`desktop/ui/` is plain HTML/CSS/JS with no bundler** (`frontendDist` points straight at it; npm is only there to vendor the Tauri CLI) — the same no-build-pipeline rule as the main repo. Its palette is **hand-copied hex** from `design.md` §2 into `ui/style.css`, deliberately not shared with Tailwind, so a future recolor of the design tokens needs a manual edit in that file too — it won't cascade.
- **The queue only holds retryable failures.** `PostError.retryable` in `main.rs` is the whole distinction: network errors/5xx/429/408 queue for the 30s background flusher; 401/400 do not (an unchanged payload will fail against them forever) and surface to the user instead. `flush_queue` stops at the *first* failure rather than skipping past it — the queue is chronological, and a bad token fails every item identically.
- **`core/api.py::ALLOWED_SOURCES` is a whitelist because `InboxItem.source` has no `choices` validation** — a client-declared `source` would otherwise be stored verbatim. `"web"`/`"review"` are server-owned and a client claiming either falls back to `"shortcut"`.
- **Rust tests: `cd desktop/src-tauri && cargo test`** (5 tests, pure decision logic only — the retryable-status rule and the `Settings` helpers). The queue's read/flush cycle can't reach them (it needs a live `AppHandle`), so it's verified instead by staging an entry into `queue.json` in the app-data dir and letting the running app's 30s flusher drain it against a live dev server — no GUI input required, since the flusher doesn't care how an entry got queued.
- **`tauri build` succeeding is NOT evidence that `Cargo.toml`'s features and `tauri.conf.json` agree — only raw `cargo` enforces that check.** A missing `app.macOSPrivateApi: true` against an enabled `macos-private-api` feature shipped a silently-opaque window through many green `tauri build`s and only surfaced when `cargo test` refused to compile. After changing Tauri features or config, run `cargo test`/`cargo build` too, not just a bundle build.
- **macOS is user-verified (manual UI pass); Windows now builds, installs (elevated NSIS `/S`, lands in `Program Files` with a Start Menu shortcut), and its offline-queue-to-server path is verified end-to-end against a real local dev server.** Still unchecked on Windows: the capture window's visual appearance, the hotkey actually firing on a keypress, and the tray menu being clickable. ## Product summary

A single-user, self-hosted Getting Things Done (GTD) task system for Sudipto: capture → clarify → organize → reflect → engage, with two-way Google Calendar time-blocking, guided review wizards with an Eisenhower triage board, ntfy push notifications, and a stats page.

**Planned stack** (per `solution-plan.md`): Django 5.x + HTMX + Alpine.js + Tailwind CSS (standalone CLI, no bundler, output committed) + PostgreSQL. Single app `core`. No Celery/queue — background work runs via cron-triggered `manage.py` commands (see the cron table in Step 12). Deployed like the existing `tracker.sudipto.dev` pattern: EC2 Ubuntu, gunicorn + nginx + systemd.

## Architecture (once implemented)

Five subsystems inside one Django project/app-server:
1. **Core GTD engine** — models (`Task`, `InboxItem`, `Note`, `Tag`, `Area`), clarify wizard, contexts/tags, horizons (`today`/`this_week`/`this_month`/`anytime`), manual sort ordering.
2. **Recurrence engine** — `RecurringTemplate` → materialized `Task` instances (one per occurrence), overdue instances pile up rather than replacing each other.
3. **Calendar subsystem** — Google OAuth, dedicated secondary "GTD" calendar (write target) + primary calendar read-only busy overlay, two-way sync via webhook + 15-min polling fallback, missed-block detection.
4. **Reflect subsystem** — `ReviewConfig`/`ReviewSession`, guided weekly/monthly wizards, lighter quarterly/yearly checklists, the Eisenhower board (drag-only, in-review, never persisted as task metadata), Big-3 stars, carry-over decision gate.
5. **Notification subsystem** — ntfy.sh dispatch with per-kind dedupe (`NotificationLog`) and digest batching.

Key domain rules to preserve when implementing (see `solution-plan.md` Step 2 "Semantics to enforce in code"):
- A project is `Task(is_project=True, parent=None)`; subtasks are one level deep only (enforced by a `CheckConstraint`).
- Next-action resolution is a single queryset helper: explicit flagged subtask(s) → else first incomplete subtask by `sort_order` (marked `implicit=True`) → else project state `NEEDS_ATTENTION`.
- There is no stored priority/quadrant field anywhere — priority is manual `sort_order` + weekly `big3` stars (auto-cleared each review) + a transient `q2_week` chip (expires the following Monday). The Eisenhower board is a review-time-only UI, not a data model.
- Trash is a soft-delete (`list=TRASH` / `trashed_at`), purged by cron after 30 days.

## Design system rules (from `docs/design.md`)

- No dynamically-constructed Tailwind class names (`bg-{{ color }}` is forbidden because of purge) — status→class mappings must return full literal strings, added to the Tailwind safelist.
- Badges are a closed vocabulary (§6 of `design.md`) — don't invent new badge/color pairings without updating that file first.
- Dark mode is out of scope for v1; don't add `dark:` variants.
- All dates/times render in Asia/Dhaka, mono typeface.
- HTMX handles all mutations (server returns partials); Alpine is for local UI state only, never a data source — the server is truth.
