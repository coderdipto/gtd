## How to read this breakdown

- "Tests" lines from the solution plan are kept as explicit subtasks, not folded in — they're the acceptance criteria per step.

## Post-v1 — Desktop capture client (`desktop/`)

Not part of the original 12 epics; requested after v1 was functionally complete. A capture-only Tauri 2 app for macOS/Windows — the desktop equivalent of the PWA's capture screen, reachable on a global hotkey so a thought never has to survive "find the browser tab."

- [x] Tauri 2 scaffold, `desktop/` (Rust + plain HTML/CSS/JS frontend, **no bundler** — `frontendDist` points straight at `ui/`, npm vendors only the Tauri CLI). Palette hand-copied from `docs/design.md` §2 into `ui/style.css`; it does **not** share Tailwind's tokens, so a future recolor needs a manual edit here too.
- [x] Menu-bar/tray app (macOS `ActivationPolicy::Accessory` — no dock icon), frameless always-on-top capture window, hidden by default; close/blur hides rather than exits.
- [x] Global hotkey (default `CmdOrCtrl+Shift+Space`, configurable), Esc/backdrop-click to dismiss, Enter to capture.
- [x] Offline queue: retryable failures (network/5xx/429) → `queue.json` in the app-data dir, flushed by a 30s background task + a tray "Send pending now". Non-retryable (401/400) deliberately **not** queued — they'd fail identically forever — and surface as an error instead.
- [x] Server side: `core/api.py` now accepts a client-declared `source` from a closed whitelist (`shortcut`/`desktop`), defaulting to `shortcut`. No migration — `source` is an unconstrained `CharField` and its default is unchanged.
- [x] **Test:** 2 new tests (14/14 in `CaptureApiTests`) — `source: "desktop"` is recorded; an unknown/server-owned source (`"web"`) falls back to `shortcut`.

**What was actually verified** (and what wasn't — same spirit as the Epic 8/10/12 caveats):

- Verified: release bundle builds (`.app` + 2.9MB `.dmg`, aarch64); the binary launches and survives with no stderr, so `setup()`'s tray build and the `CmdOrCtrl+Shift+Space` registration both succeed on macOS; the HTTP contract against a real local dev server — 201 on a valid `source: "desktop"` capture (item stored with the right title/description/source), 401 `{"detail": "invalid token"}`, and 400 `{"detail": "title is required"}`, all three matching what `main.rs` parses.
- Verified by the user, manually, on macOS: the UI works — the capture window looks and behaves right. An eyeball pass, not an exhaustive one.
- Verified: **the offline queue drains end-to-end, for real.** A `queue.json` entry staged by hand into the app-data dir (`~/Library/Application Support/dev.sudipto.gtd.capture/`) was picked up by the running app's 30s background flusher and POSTed to a live dev server — the `InboxItem` landed with `source="desktop"` and the `CaptureToken`'s `last_used_at` updated. Staging the file directly is the trick worth remembering: the flusher doesn't care how an entry got into the queue, so the whole read → POST → drop-on-success cycle is testable without any GUI input.
- Verified: 5 Rust unit tests (`cargo test` in `src-tauri/`) over the pure decision logic — `status_is_retryable` (5xx/429/408 retry; 401/400/403/404 don't), `Settings::capture_url` (trailing-slash/whitespace tolerance), `Settings::configured`. The retryable rule was extracted out of `post_item` into its own function to make it reachable without a live HTTP response.
- **Resolved by reading, no longer an open question:** the `Focused(false)` "double-fire" worry was a non-issue. The backdrop is a DOM element *inside* the webview, so clicking it never blurs the window — the blur path only fires when another app takes focus, making them separate scenarios rather than a race. Even if both fired, they converge on the same idempotent `hide_window` command, and the only toggle (`toggle_capture`) is reachable solely from the hotkey. The blur handler also guards on both fields being empty, so it can't discard half-typed text.
- **Not verified: Windows, at all.** Never built there, let alone run — the accelerator-string parsing and tray behavior are still reasoned-about only. Planned for later.
- Not verified: that the tray menu items are actually *clickable*. "Send pending now" calls the same `flush_queue` the timer does (now verified), so only the menu wiring itself is unproven.
- Fixed during the build, worth knowing about: `setup()` originally emitted `show-view: settings` on first run, which races the webview's load and can be dropped — a first-run user would land on an unconfigurable capture box. The initial view is now chosen by `ui/app.js::init` after the frontend exists. Any future "tell the frontend something at startup" needs the same treatment.
- **Found while adding the Rust tests: `tauri.conf.json` was missing `app.macOSPrivateApi: true`** while `Cargo.toml` enabled the paired `macos-private-api` feature — the exact mismatch `Cargo.toml`'s own comment warns about ("both are needed, neither alone does anything"). Consequence: window transparency silently never took effect, so the frameless card sat on an opaque white NSWindow. **The Tauri CLI does not enforce this check — only raw `cargo` does**, which is why `tauri build` kept producing a working-looking `.dmg` and nothing surfaced it until `cargo test` refused to compile. Worth remembering generally: `tauri build` succeeding is not evidence that the Cargo features and the config agree.

**Deliberate scope cuts:** builds are ad-hoc signed (`signingIdentity: "-"`), not Developer-ID signed — verified sufficient for the build-it-and-run-it-here case, since Gatekeeper only evaluates apps carrying a download-attached `com.apple.quarantine` xattr, which a locally-compiled app never has. (`spctl -a` reports "rejected" regardless; that verdict is only consulted for quarantined apps, so it isn't the thing to check.) A Developer ID would only be needed to hand the `.dmg` to another machine — **which the `desktop-v0.1.0` GitHub release now does** (see below), so that cut is now load-bearing in a way it wasn't. No cross-compilation — each platform's installer is built on that platform. The token sits in plaintext in `settings.json`, acceptable *only* because a `CaptureToken` can create inbox items and nothing else; don't reuse that posture for a wider-scoped credential.

**Releases:** tagged `desktop-v0.1.0` (prefixed, not a bare `v0.1.0` — this repo is the whole GTD app, and the desktop client versions independently of the web app), published as a **prerelease** on GitHub with the Apple Silicon `.dmg` attached. Because the build is unsigned, a downloaded copy carries `com.apple.quarantine` and Gatekeeper rejects it with a misleading **"GTD Capture is damaged and can't be opened"** — so the release notes carry the `xattr -dr com.apple.quarantine "/Applications/GTD Capture.app"` workaround. That command is verified to work (quarantine flag applied to a copy from the published `.dmg`, then removed by it); the resulting *launch* wasn't tested, to avoid a second instance fighting the running one over the global hotkey. Upgrading to a real Developer ID + notarization (`APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID`, which Tauri supports natively) is the fix if this ever needs to install cleanly for anyone who won't paste a terminal command.
